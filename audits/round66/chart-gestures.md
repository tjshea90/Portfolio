# Round 66 audit - PriceChart.kt chart gestures

Scope: `app/src/main/java/com/tj/portfolio/ui/PriceChart.kt` (pointer state machine,
zoom/pan arithmetic, scrub caption vs crosshair), with `data/ChartWindow.kt` and
`data/ChartModels.kt` read as supporting evidence. Read-only.

---

ID: CHT-1
SEVERITY: MEDIUM
WHERE: app/src/main/java/com/tj/portfolio/ui/PriceChart.kt:1983-2001 (with `centroidX`, PriceChart.kt:2159-2164)
BUG: The two-finger pan compares this frame's `centroidX` against the previous frame's even when the NUMBER of pointers changed, so a third finger landing (or lifting) during a pinch is reported to `onPan` as a large, real hand movement.
FAILURE: `pair` is only re-chosen (and `centroid` only reset to NaN, line 1966) when one of the two MEASURED fingers has gone. A third pointer changes `centroidX` without touching the pair, so `zoomFactor` returns non-null and the reset at 1961-1968 is skipped. Concrete, width = 1080px: fingers A at x=100 and B at x=300 are pinching, `centroid` = 200. A third pointer (a resting palm, a steadying thumb) lands at x=1000 on frame N. `zoomFactor(event, A, B)` still returns a valid ratio, so line 1983 computes `mid = (100+300+1000)/3 = 466.7`, line 1995 computes `moved = 466.7 - 200 = 266.7`, and line 1998 calls `onPan(-0.247)` - a quarter of the visible span, in one frame, from a finger that only touched down. When that finger lifts, `mid` snaps back to 200 and an equal-and-opposite jump is reported. Each jump goes through the caller's `pan` provider (PriceChart.kt:405-428, `send(next)` at 426) so it also reaches `onWindow` and can trigger a range refetch. `centroidX`'s own doc comment (2154-2157) states the opposite guarantee: "a third finger landing should not make the window jump".
FIX: Track the pointer count the previous centroid was measured over. Add `var centroidN = 0` beside `centroid` (declared at PriceChart.kt:1876), set it to the pressed count each time `centroid = mid` is written (line 2001) and to 0 wherever `centroid = Float.NaN` is written (lines 1876, 1948, 1966), then gate the pan on it: `if (onPan != null && centroid.isFinite() && centroidN == pressed)`. A frame where the count changed simply re-seeds the reference and reports no pan, exactly as the pair-changed path at 1961-1968 already does.
CONFIDENCE: certain

ID: CHT-2
SEVERITY: MEDIUM
WHERE: app/src/main/java/com/tj/portfolio/ui/PriceChart.kt:2019-2024
BUG: `GestureMode.ZOOM` latches until EVERY finger lifts, so when one finger of a pinch leaves and the other keeps dragging, the loop consumes every remaining event and does nothing with it - the chart is frozen and the page underneath cannot scroll either.
FAILURE: Zoomed chart on the detail screen. `down(0)` at x=800, `down(1)` at x=300 -> line 1940 sets `mode = ZOOM`, `report(ChartGesture.ZOOM)` (so `gestureLive`/`chartPinching` are true). Spread to size the window. Now `up(1)`: the next event has `pressed == 1`, so the two-finger branch at 1938 is skipped and control reaches 2019, which consumes the one pressed change and `continue`s. Every subsequent frame does the same: `mode` can never leave ZOOM (nothing assigns it except the ZOOM entry at 1941 and the UNDECIDED block at 2053-2078, which is unreachable once `mode != UNDECIDED`). Drag the surviving finger 400px left: the window does not move, no crosshair appears, and because line 2022 consumes, the enclosing `verticalScroll` gets nothing either. The chart is inert until the last finger lifts. Note the doc at 1775-1777 only requires that the tail of a pinch "must not turn into a scrub"; the comment at 2072-2074 explicitly justifies re-reading `canPan()` at decision time "so a pinch that ends with one finger down leaves the right gesture behind it" - a path line 2019 makes unreachable. Not covered: every multi-touch test in ContinuousZoomUiTest.kt and PanGestureUiTest.kt lifts both pointers together (`up(0); up(1)`).
FIX: At 2019, let a pinch that has dropped to one finger become a PAN (never a SCRUB, so the documented rule is kept): `if (mode == GestureMode.ZOOM) { if (pressed == 1 && canPan() && onPan != null) mode = GestureMode.PAN else { event.changes.forEach { if (it.pressed) it.consume() }; continue } }`. Control then falls through to 2026 and the existing `GestureMode.PAN` arm at 2085-2097, whose `report(ChartGesture.PAN)` keeps `held.window` (line 456-458 only re-seeds when it is null), so the pan continues from where the pinch left the window. A second finger landing again re-enters ZOOM normally at 1938-1941.
CONFIDENCE: certain

ID: CHT-3
SEVERITY: MEDIUM
WHERE: app/src/main/java/com/tj/portfolio/ui/PriceChart.kt:1654-1660 (`nearestIndex` clamp) vs 1573-1592 (crosshair) and 1013-1053 (`ChartReadout` scrubbed branch)
BUG: When the window falls entirely between two candles, `nearestIndex`'s "never on a point that is not on screen" clamp is skipped, so the readout prints a price and a timestamp from a point outside the window while the crosshair that is supposed to show where that price came from is drawn off-canvas and clipped away.
FAILURE: Zoom into the middle of a 5Y (weekly) or All (monthly) chart. `ChartWindow.MIN_SPAN_MS` is 30 minutes, and `rangeForLookback` keeps the coarse range for a window panned into the past, so a 30-minute window between two weekly candles is reachable in one pinch. `clipToWindow` then hands the canvas the straddling pair (the `hi < lo` branch at 2564-2575), `insideIndices` falls back to `pts.indices` (2518), and in `nearestIndex` `firstIn` = 1 while `lastIn` = 0, so `firstIn in 0..lastIn` is false at line 1659 and `best` is left at whichever straddling point is nearer in time - a point weeks outside the window. Drawing: `x(p) = w * (p.t - t0) / tSpan` with `tSpan` = 1800s and `p.t - t0` measured in weeks gives `px` on the order of ±300*w, so `drawLine(Offset(px,0), Offset(px,h))` at 1578-1582 and both `drawCircle` calls at 1585-1586 land far outside the plot and are removed by the `.clipToBounds()` at line 619. Result under the finger: `Fmt.price(point.close)` plus `axisLabel(point.t * 1000L, ...)` naming a date weeks away from the two dates the x-axis prints below the chart (lines 774-786), a change/percent computed from it - and no crosshair anywhere on screen. The comment at 1650-1651 describes exactly this symptom as the bug the clamp was added to fix; the fallback at 1652-1653 re-opens it.
FIX: Make the degenerate case return "nothing under the finger" rather than a point off screen. In `PriceChart`'s `pointAt` (lines 364-370) reject the result when it falls outside the axis: after computing the index, `scrub.intValue = idx.takeIf { val t = pts[it].t * 1000L; t >= axisW.startMs && t <= axisW.endMs } ?: NO_SCRUB` (with `axisW = liveAxis.value`, and keeping the current behaviour when it is null). Both the readout (`i in s.points.indices` at 958) and the crosshair (`i in pts.indices` at 1574) already treat `NO_SCRUB` as "nothing under the finger", so they stay in agreement instead of disagreeing.
CONFIDENCE: certain

ID: CHT-4
SEVERITY: LOW
WHERE: app/src/main/java/com/tj/portfolio/ui/PriceChart.kt:292-296 (predicate) vs 1910-1911 and 2057 (hold) and 408 (pan provider)
BUG: `canPanNow` - the one predicate the caption and the gesture are supposed to share - tests `onWindow != null` but not `windowBounds != null`, while `pan()` needs both; so on a chart given a `window` and an `onWindow` but no `windowBounds` the caption promises "drag to move, hold to scrub" and the press-and-hold still arms, for a pan that cannot exist.
FAILURE: `windowBounds` is an independent optional parameter defaulting to null (line 135), exactly the shape sweep 2 / N05 closed for `onWindow`. With `window` = the middle third of the series, `onWindow` non-null and `windowBounds` null: `canPanNow` at 292-296 is true, so line 892 appends ", drag to move, hold to scrub" to the caption. But `pan = { ... if (send == null || b == null) null ... }` (line 408) returns null, so the drag decision at 2075 falls back to `GestureMode.SCRUB` - the caption names a gesture that scrubs instead. Worse, `holdPossible` (1910-1911) and the in-loop arm (2057) test only `canPan()`, not `onPan != null`, so the hold DOES arm: after 350ms of stillness the chart fires a haptic tick, sets `mode = SCRUB` and consumes from that moment on - before the touch slop - so a press that pauses and then turns into a page scroll stops the page dead. That is precisely the N01 harm the hold's own note (1902-1909) says must not happen on a chart shape where the hold changes nothing. Latent rather than live today: both shipped call sites (DetailScreen.kt:986-987, 785-786) derive `windowBounds` from the same series `canPanNow` measures against, and PriceChart's own `seriesWindowAll != null` clause rules out the degenerate cases - but that is the caller's property, not this file's.
FIX: Add the missing clause to the one predicate: at 292-296 make it `canReportWindow && windowBounds != null && window != null && seriesWindowAll != null && window.spanMs < seriesWindowAll.spanMs`, and add `windowBounds` to the `remember` keys. Optionally also tighten 1910-1911 and 2057 to `canPan() && onPan != null` so the hold and the drag decision at 2075 test the same thing.
CONFIDENCE: certain
